# CodeSage Tech Stack

Every language, framework, library and tool CodeSage uses (Phases 1–4): its
version, what it does, and where it shows up in the code. Versions are the exact
ones pinned in `backend/requirements*.txt` and `frontend/package-lock.json`.

## At a glance

```
┌──────────────────────────── Browser ────────────────────────────┐
│  Next.js 16 · React 19 · TypeScript 5 · Tailwind CSS 4           │   frontend/   (npm run dev → :3000)
└──────────────────────────────┬───────────────────────────────────┘
                               │ HTTP + JSON  (fetch, CORS)  /api/v1/...
┌──────────────────────────────▼───────────────────────────────────┐
│  Uvicorn (server) → FastAPI (framework) → Pydantic (validation)  │   backend/    (uvicorn → :8000)
│  Services → Repositories → SQLAlchemy ORM                        │
│  Job threads → Git CLI (clone) → scanner (read-only)  ──▶ GitHub │   data/repositories/
│  Tree-sitter (parse) → chunker → BM25 (NumPy) + BGE/ONNX → FAISS │   data/indexes/, data/models/
└──────────────────────────────┬───────────────────────────────────┘
                               │ SQL  (psycopg driver)
┌──────────────────────────────▼───────────────────────────────────┐
│  PostgreSQL          (schema managed by Alembic migrations)      │   system service (:5432)
└──────────────────────────────────────────────────────────────────┘
```

| Layer | Main technologies |
| --- | --- |
| Frontend | Next.js, React, TypeScript, Tailwind CSS |
| Backend | Python, FastAPI, Uvicorn, Pydantic, SQLAlchemy, Alembic |
| Ingestion | Git CLI, Python `subprocess` / `hashlib` / `concurrent.futures` |
| Code analysis | Tree-sitter + grammars for Python, JavaScript, TypeScript/TSX |
| Retrieval | NumPy BM25, fastembed + ONNX Runtime (BGE), FAISS, cross-encoder reranking |
| Database | PostgreSQL (SQLite in-memory for tests) |
| Testing & quality | pytest, Ruff, ESLint, TypeScript compiler |
| Tooling | venv + pip, npm, Bash scripts, `.env` files, Swagger UI |

| Technology | Version | What it is | How CodeSage uses it | Where |
| --- | --- | --- | --- | --- |
| **NumPy** | 2.3.4 | Array maths. | BM25 itself: an inverted index of postings, term frequencies and document lengths, scored with vectorised array operations and saved as a compressed `.npz`. Also normalises embeddings. | `app/retrieval/bm25.py`, `embeddings.py` |
| **fastembed** | 0.8.0 | Embedding library that runs quantised ONNX models locally — no PyTorch. | `FastEmbedProvider`: turns chunks and queries into BGE vectors on the CPU; also provides the cross-encoder reranker (`TextCrossEncoder`). | **onnxruntime** | 1.30.0 (installed with fastembed) | Runtime that executes ONNX neural networks. | Runs the embedding and reranking models; `EMBEDDING_THREADS` maps to its thread count. | — |
| **faiss-cpu** | 1.15.1 | Meta's vector similarity library. | `FaissVectorStore`: an `IndexFlatIP` over L2-normalised vectors, i.e. exact cosine similarity, with an ids sidecar. Saved next to the BM25 files. | `app/retrieval/vector_store.py` |
| **BAAI/bge-small-en-v1.5** | — (model, ~100 MB) | Small English embedding model, 384 dimensions. | The default `EMBEDDING_MODEL`. Its recommended query instruction is applied to queries only. | `EMBEDDING_MODEL` |
| **Xenova/ms-marco-MiniLM-L-6-v2** | — (model) | Cross-encoder trained on MS MARCO. | The default reranker: scores query and chunk together for the `hybrid_rerank` strategy. | `RERANKER_MODEL` |

**Why fastembed instead of sentence-transformers?** Both reach the same ~1,300
tokens/s on this machine, but fastembed installs 241 MB instead of 1.1 GB (no
PyTorch), behaves the same on every platform, and ships int8-quantised ONNX
models. The model is reachable only through `EmbeddingProvider`, so swapping in
sentence-transformers or a hosted API is one class.

**Why write BM25 by hand?** About 100 lines of NumPy gives exactly what is
needed — a persistable inverted index, configurable `k1`/`b`, and a tokenizer
that understands `camelCase`, `snake_case` and file paths, which is the part
that matters for code. `rank_bm25` keeps everything in Python lists and has no
persistence.

**Why Tree-sitter instead of Python's `ast` module or the TypeScript compiler?** One API
for every language (new languages are a grammar package away), it keeps working on files
with syntax errors, gives exact line ranges, and it is pure parsing — nothing is imported
or executed. Python's `ast` handles only Python; the TypeScript compiler needs Node.js
and a project build.

**Why the Git CLI instead of GitPython or dulwich?** The CLI is the reference
implementation, needs no extra dependency, and is easy to sandbox (explicit
arguments, environment and `-c` overrides). GitPython itself shells out to the
same CLI; dulwich reimplements git and lags behind it.

**Backend architecture patterns** (explained in [architecture.md](architecture.md))

| Pattern | What it means here | Where |
| --- | --- | --- |
| Layered architecture | Endpoints → services → repositories → models; each layer has one job. | `app/api`, `app/services`, `app/repositories`, `app/models` |
| Repository pattern | All database queries live in data-access classes, not in endpoints. | `app/repositories/` |
| Dependency injection | FastAPI builds sessions/services per request; tests swap them out. | `app/api/deps.py` |
| Application factory | `create_app(settings)` builds the app, so tests can use their own settings. | `app/main.py` |
| API versioning | Every route lives under `/api/v1`. | `app/api/v1/router.py` |
| Uniform error envelope | Every error returns `{"error": {code, message, details, request_id}}`. | `app/core/exceptions.py` |
| Job queue abstraction | Services enqueue named jobs with string payloads; a thread pool runs them today, a broker (Celery/RQ) can later. | `app/jobs/` |
| Domain errors vs HTTP errors | The ingestion package raises `IngestionError`s; the service layer translates them to HTTP status codes. | `app/services/repository_service.py` |
| Strategy + registry (analyzers) | Each language implements `LanguageAnalyzer`; a registry picks one by file extension, so languages are added without touching the pipeline. | `app/analysis/registry.py` |
| Strategy (retrievers) | Each retrieval strategy implements `Retriever` and composes: hybrid wraps BM25 + dense, reranking wraps hybrid. Adding one does not touch the endpoint. | `app/retrieval/engine.py` |
| Provider abstractions | `EmbeddingProvider`, `VectorStore` and `Reranker` are interfaces; the model and store are named once in configuration. | `app/retrieval/` |

## 4. Database

| Technology | Version | Used for | Details |
| --- | --- | --- | --- |
| **PostgreSQL** | 14 or newer (developed on 16) | The main data store: users, projects, repositories, indexing jobs, the file index, code symbols/imports and the dependency graph. | Runs as a normal service on `localhost:5432`, database `codesage`, user `codesage`. Uses `uuid` primary keys, `timestamptz` timestamps, foreign keys with `CASCADE`/`SET NULL`, and unique constraints. |
| **SQLite** | built into Python | Fast, throwaway database for the test suite. | Tests use an in-memory SQLite database, so `pytest` needs no running server. Set `TEST_DATABASE_URL` to run the same tests on PostgreSQL. |

**Tables:** `users` 1 → * `projects` 1 → * `repositories` 1 → * `indexing_jobs` /
`repository_files` / `code_files` (→ `code_symbols`, `code_imports`) /
`code_relationships` / `code_chunks` / `retrieval_logs`, plus `alembic_version`
(Alembic's record of the applied migration). Uses a JSON column for extracted metadata and a partial unique index
(one active job per repository). Column-level
details are in [architecture.md](architecture.md#data-model).

**Why PostgreSQL:** reliable relational integrity (foreign keys, unique
constraints, transactions) for the core data, excellent SQLAlchemy/Alembic
support, and a path to vector search inside the same database (`pgvector`) that
later retrieval phases may use.

## 7. Why these choices

| Choice | Instead of | Reason |
| --- | --- | --- |
| **FastAPI** | Flask, Django | Type hints drive validation and API docs automatically; async-capable for future LLM and retrieval calls; small and explicit (Django brings much we don't need). |
| **Pydantic** | manual validation | Declarative, typed schemas shared by validation, serialisation and docs. |
| **SQLAlchemy 2 + Alembic** | raw SQL, Django ORM | The standard Python ORM, works with any SQL database, and Alembic gives reviewable, reversible migrations. |
| **PostgreSQL** | MySQL, MongoDB | Strong relational integrity for projects/repositories, first-class JSON support, and `pgvector` as a future option for embeddings. |
| **Next.js** | plain React + Vite | Routing, layouts, error/loading boundaries and an optimised production build out of the box. |
| **TypeScript** | JavaScript | Catches API-contract mistakes at build time instead of in the browser. |
| **Tailwind CSS** | hand-written CSS, component kits | Consistent styling without a separate CSS file per component or a heavy UI dependency. |
| **Ruff** | flake8 + isort + black | One fast tool for linting and formatting. |

## 9. Deliberately not used (for now)

| Not used | Why |
| --- | --- |
| Docker / Docker Compose | Removed by choice: the backend and frontend run directly in two terminals, and PostgreSQL runs as a local service. |
| Authentication library | Authentication is not built yet; the `users` table is ready for it. |
| React Query / SWR | The small `useApi` + `useInterval` hooks cover fetching, retry and polling. |
| UI component or icon libraries | Only a handful of components and icons are needed. |
| Async SQLAlchemy | Synchronous sessions are simpler; FastAPI runs synchronous endpoints in a thread pool. |
| Redis / Celery / RQ | Phase 2's in-process thread pool is enough for one API process; the job abstraction lets a broker replace it without changing services or handlers. |
| GitPython / dulwich | The Git CLI, run directly and hardened, is simpler to sandbox and adds no dependency. |
| Graph / chart libraries (D3, Cytoscape, React Flow) | The Phase 3 dependency view is a small neighbourhood diagram; a few lines of SVG are enough. |
| Syntax-highlighting library | Kept out of Phase 3 to stay dependency-free; the source viewer shows plain text with line numbers. |
| PyTorch / sentence-transformers | fastembed's ONNX models are the same speed here at a fifth of the install size. |
| `rank_bm25` or Elasticsearch | ~100 lines of NumPy cover BM25 with persistence and code-aware tokenisation; a search server is a lot of operations for one index. |
| LangChain / LlamaIndex | The chunking, retrieval and fusion here are small, explicit and measurable; a framework would hide exactly the parts this project is researching. |
| WebSockets / server-sent events for progress | Polling every 2 s is simpler and good enough for indexing that takes seconds to minutes. |

## Where versions are pinned and how to upgrade

| Side | Pinned in | Upgrade |
| --- | --- | --- |
| Backend | `backend/requirements.txt` (runtime) and `requirements-dev.txt` (tests/lint), exact `==` versions | Edit the version, `pip install -r requirements-dev.txt`, then run `pytest` and `ruff check .` |
| Frontend | `frontend/package.json` (allowed ranges) and `package-lock.json` (exact versions) | `npm install <package>@<version>`, then `npm run lint`, `npm run typecheck`, `npm run build` |

Known constraint: ESLint stays on version 9 because several plugins used by
`eslint-config-next` do not support ESLint 10 yet.
